# 判定结果契约（R1 · 只读阶段）

> 目的：把"成功"这件事的**证明边界**写清楚，作为合成测试的独立规格。
> 本轮**不修改** `SuccessRule` 的生产判定条件。
> 规格来源：用户决策（宁可漏判不误判 / 未知不得当失败 / 时间不能单独结案）+ 判定链三道前置闸门的设计意图。
> **不是**从生产代码反推的。

---

## 1. 三个必须分清的概念

| 概念 | 含义 | 谁能证明它 |
|---|---|---|
| **认证成功** | 这条候选口令与 AP 的 PSK 一致（4 次握手完成） | `Supplicant state: COMPLETED` + 有效 IP（协议层事实） |
| **候选归因** | 此刻这条连接**是本条候选**发起的，而不是旧配置/缓存/系统回连 | 候选级标识（本条尝试创建的配置 netId + 尝试 id） |
| **业务失败** | 这条候选**已被证明**不可能成功（不是"还没看到成功"） | 只能由**正面信号**证明（见 §5） |

**现状的关键事实**：`SuccessRule.isSuccess()` 只覆盖"认证成功"**前三项**（SSID + COMPLETED + IP），
**完全不参与"候选归因"** —— 归因由发令前的三道闸门（删净 / 净检 / 断开确认）承担。
所以现状的证明强度是：**「三条件成立 + 闸门曾经成功」**，而不是「这条连接确属本条候选」。

---

## 2. netId 能证明什么、不能证明什么

**能证明**
- 系统里**存在**一条对应本目标 SSID 的配置，且它的编号是 N（结构性事实，与时间无关）；
- 若 `status.Net ID == N`，则**当前这条连接用的就是编号为 N 的配置** —— 这是"连接↔配置"的硬绑定；
- 配合"发令前已把目标配置删净并回读确认"，编号 N 的配置**只可能由本条尝试创建** ⇒
  `status.Net ID == 本条探测到的 netId` 是**候选归因的充分证据**。

**不能证明**
- 不能证明口令正确（口令正确与否由握手完成证明，与编号无关）；
- 不能证明"这条配置是本次尝试建的" —— 若同目标存在**同号复用**或框架在探测之后**重建**了配置，
  编号会漂移；因此"编号不等"只能说明"**这条连接不来自我们探测到的那条配置**"，不能反推是谁建的；
- 框架**可能根本不回报** netId（实测探测会在 242~324ms 后才出现；缺失时该值 = -1）；
- netId 是**进程级易失标识**（重启、重新添加配置都会变），不可持久化比对。

**因此**：netId 只能作为**条件否决**（两侧都拿到有效值时才比较），不能作为**必要条件**
（缺失时不得据此判否 —— 这正是历史上"硬要求 netId 相等 → 正确密码永远判不出来"的成因）。

---

## 3. 现状契约（三条件）与它的保证边界

```
SUCCESS  ⇔  status.SSID == target.SSID
         ∧  status.state == "COMPLETED"            （大小写不敏感）
         ∧  status.ip 非空 且 != "0.0.0.0"
```

**保证**：不会把"没连上"报成成功；不会把 SSID 不同的网络报成成功。
**不保证**：连上的**是不是本条候选**。这一点完全外包给三道前置闸门。

推论（必须写进结论）：**闸门失败 = 成功判定失去归因**。因此闸门的失败必须导致**非成功**结果
（现状已经是：三处闸门失败都返回 `UNKNOWN`）—— 这一点是现状为数不多做对的地方。

---

## 4. 提案契约（候选级绑定，尚未落地）

在现状三条件之上，追加一条**条件否决**：

```
若 (targetNetId > 0 ∧ statusNetId > 0)：          // 两侧都有有效值才比较
       要求 statusNetId == targetNetId             // 否则 → 非 SUCCESS（记 UNKNOWN_NETID_MISMATCH）
否则：                                              // 任一侧缺失/无效
       退回现状三条件（不得否决）
```

**新增结果语义**：`UNKNOWN_NETID_MISMATCH` —— "连接成立，但归属不匹配"。
它是一个**独立状态**，既不能记成功，也**不得写成 AUTH_FAIL**（见契约 §1 第 3 行）。

## 6. 恢复否决会引入的漏判风险（逐条列出，供确认）

| ID | 风险 | 触发条件 | 量级评估 | 缓解 |
|---|---|---|---|---|
| F1 | 框架在探测之后**重建**了配置（编号漂移） | 少数 ROM 在连接建立时会重写配置 | 低（本机未观测到） | 只在"两侧都拿到"时否决；漂移成新号时会命中 #2 → 变成 UNKNOWN（安全但漏判） |
| F2 | 目标 SSID 存在**多条**配置（本机实测曾出现同一 SSID 两行、但同号） | 用户手动保存过、或系统重建 | 中 | 否决只在两侧都 > 0 时生效；另外闸门①已要求删净 |
| F3 | `status.Net ID` 在**连接切换过程中**短暂指向旧连接 | 密集切换 | 低 | 每轮重读；一旦出现 SUCCESS 的其它条件也会同轮满足 → 级联判断 |
| F4 | 探测窗口内没拿到 netId（>4 轮） → targetNetId = -1 | 慢机/忙时 | **中** | 提案**不否决**（退回三条件）→ 保持现状行为，仅损失加固性 |
| F5 | 与 #2 相邻的边界：`statusNetId` 有效但属于**本目标的另一条**合法配置（例如我们上一条留下的） | 闸门③未确认断开时 | 低（闸门③已拦） | 现状与提案都不误判成功；提案会把它记成 UNKNOWN_MISMATCH |

**结论**：提案的漏判面**小于**它堵住的误判面；且所有漏判都落在"UNKNOWN（非成功、诚实体现在文案）"，
**不会**产生假成功。F4 是最需要盯的一条（依赖探测可靠性）。

## 7. 旧任务证据混淆的窗口（用户第 3 项）

可混淆的证据与其归属手段：

| 证据 | 归属手段 | 现状是否足够 |
|---|---|---|
| `logcat` 握手行 | 每条候选前 `logcat -c`；且要求"关联行 SSID == 目标" | ⚠ 日志配额可让整段消失（丢失 ≠ 未发生） |
| 系统广播（认证失败） | 时间界 `commandAt` + 120ms 复核 | ⚠ 上一条的**迟到广播**接收时刻可落在本条之后 |
| `status` / netId | 连续轮询 + 闸门前置 | ⚠ 无 attemptId，无法证明"这条连接属于本次尝试" |
| 队列持久化状态 | 任务 id | ✅ 有 id |

**唯一的结构性修法**：引入 **attemptId**（每次尝试自增，写入该尝试产生的全部日志与判定），
让"证据属于哪次尝试"可证。这是 R6，与 R1 互为前提（R1 的否决要想被信任，也需要它）。

2. `statusNetId == 0` / `targetNetId == 0` 视为"无效值不否决"是否可接受？（表 #11/#12）
3. 若确认，落地顺序是否 R6（attemptId）→ R1（条件否决）？理由：R1 的否决在没有 attemptId 时，
   只能靠 netId 单点支撑；加上 attemptId 后，"连接属于本次尝试"才有多一重证明。
